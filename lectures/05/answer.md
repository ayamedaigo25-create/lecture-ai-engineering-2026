- 検索だけを実行して見つかったページと、その本文で確認できたこと：uv run python -m app.retrieval "LoRA QLoRA 違い" を実行したところ、第2回のPDF p.52、p.51、p.60、p.47、p.61の順に5件が取得された。p.52にはLoRAが元の重みを固定して低ランク行列A・Bだけを学習すること、QLoRAでは元の重みを4bitに量子化することが記載されていた。p.51にもPEFTの一種として両者の特徴が説明されていた。一方、p.47、p.60、p.61は関連する話題を扱っているものの、今回の質問に直接回答するためには必須ではなかった。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：全文投入：検索ツールを使用せず、資料を直接入力した。
ベクトル検索：search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'}) を1回呼び出した。
Tree：browse_tree を4回呼び出した。講義一覧から第2回「基盤モデルの仕組み」を選択し、「選んだモデルを、いつ・どう直すか」の章を経由してPDF p.52の全文を取得した。
Graph：search_graph({'query': 'LoRA 固定 学習 QLoRA'}) を1回呼び出した。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：今回の質問では、いずれの方式でも必要な根拠ページを特定できており、情報取得の明確な失敗は確認されなかった。ただし、全文投入では根拠ページを特定しながらも、質問への直接的な回答ではなくヒントが提示された。これは検索の問題ではなく、エージェントの指示文が影響した可能性がある。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：今回のような特定の概念についての質問では、基本RAGを採用したい。正確な回答を生成できたうえ、入力トークン数と推定費用が最も少なかったためである。Graphは最短時間で回答を生成したが、基本RAGより入力トークン数が多かった。Treeは資料の階層構造に沿って探索できるものの、ツール呼び出し回数が増えた。ただし、比較した質問は1問のみであり、実行ごとの検索語やモデルの応答にも差がある。また、全文投入と他の方式では対象資料数が異なるため、今回の結果だけで各方式の性能を一般化することはできない。
- 気づき・疑問：必要な根拠を取得するために、必ずしも大量の資料をモデルに渡す必要はないと分かった。一方、検索結果を多く取得しても、そのすべてが回答に必要とは限らない。質問との関連性と資料同士の関係を考慮して、取得するページを選択する方法に改善の余地があると考えた。

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：Graph検索における候補ページの優先順位付けを改良した。従来はグラフ上の距離、用語ノードの接続数、検索順位を基準にしていたが、新たに質問文と候補ページ本文のキーワード一致数を導入した。最初はキーワード一致数を最優先としたが、関連性の低いページまで取得される問題が発生した。そのため、グラフ上の距離を第一の基準とし、同じ距離の候補をキーワード一致数で順位付けするよう変更した。

変更ファイル：app/retrieval.py

- 比較した質問と、固定した条件（モデル・対象資料など）：質問：「第3回の例では、コンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか？」

条件：モデルはgemini-3.5-flash-lite、対象資料は第1〜3回の本講義214ページとした。質問文は統一したが、エージェントが生成する検索語とツール呼び出し回数には実行間で差が生じた。

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：基本RAGは5.31秒・6,617入力トークン・推定費用$0.003148、既存Graphは3.88秒・5,301入力トークン・$0.002758だった。最初の改良Graphでは5.86秒・14,042入力トークン・$0.004327となり、効率が悪化した。優先順位を再設計した最終版では4.28秒・5,373入力トークン・$0.002769となった。候補ページの順位は変化したが、回答内容には明確な改善が見られなかった。

- 気づき・疑問：Graph検索では、候補の数を増やすことよりも、質問に必要な根拠を適切に選ぶことが重要だと分かった。今後は、単純な文字列一致ではなく、質問と候補ページの意味的類似度や関係の種類を利用した順位付けを検討したい。
